# Plan 3: 投稿作成・閲覧・編集・検索

## 概要

通常のSNSとして、テキスト投稿の作成、公開タイムライン、詳細、自己投稿の本文編集、閲覧可能な投稿の本文検索を実装する。検索を含む全クエリで入力値を命令として扱わない。

共通の仕様・入力規則・ルート・対象外は[全体計画](./implementation-overview.md)を参照する。

## PR / stack構成

| 項目 | 計画値 |
| --- | --- |
| Plan | Plan 3（このPlan全体で1 PR） |
| headブランチ | `feat/sns-posts-search` |
| baseブランチ | `feat/sns-auth` |
| 直下の依存Plan | Plan 2 |
| stack位置 | middle |
| マージ順 | 3番目。Plan 1 → 2 → 3 → 4 |

## 前提条件

- Plan 2の登録・認証・CSRF・共通レイアウトが利用できる。
- 公開／非公開は作成時に指定し、編集は本文だけ。投稿者はサーバー側のログイン情報で決める。
- 閲覧可能条件は「公開、またはログイン利用者が所有する非公開」。タイムラインは公開のみ。詳細と検索で同じ条件を守る。

**特記事項**

- トランクへ機能開発を直接コミットしない。全Taskを同じheadブランチと1つのPRに含める。
- 上位Planのbaseは直下Planのheadとする。下位のマージ後は実際のトランクへ付け替え、差分を再確認する。
- サブタスクを原則1コミットとし、検証だけの作業ではコミットを作らない。テスト→実装→検証の順で進める。
- コードレビューを実施し、指摘を反映してからこのPlanのPRを1つ作成または更新する。リモート未確定ならPR作成は未完了として記録する。
- 計画作成時点では、すべてのTaskは未着手。

## 設計方針

投稿の読み書きは `src/posts/repository.js`、検索は `src/posts/search.js` に置く。認可とSQLパラメーター化を明示し、文字列結合によるクエリ生成や後で脆弱性を切り替える分岐は入れない。viewへ渡す投稿データは必要な列だけにし、ユーザーのダイジェストを取得・展開しない。

## タスク一覧

### Task 1: 投稿作成・公開一覧・詳細を実装する

**目的:** 公開範囲を持つ投稿を保存し、許可された内容だけを表示する。

**変更ファイル（作成予定）:**

- `src/posts/validation.js`
- `src/posts/repository.js`
- `src/routes/posts.js`
- `views/timeline.ejs`
- `views/posts/new.ejs`
- `views/posts/show.ejs`
- `tests/posts.test.js`

**サブタスク:**

1. [ ] **1-1** 本文境界値、未ログイン、CSRF、不正な公開フラグ、投稿者ID偽装、公開一覧、自己／他人の非公開詳細、最大50件・並び順のHTTPテストを作る。
   - 予定コミット: `test(posts): define creation and visibility contracts`
2. [ ] **1-2** 投稿作成・公開一覧・詳細のDB処理とルートを実装する。入力値はバインドし、投稿者はセッションから決め、存在しない／閲覧不可の詳細は404とする。
   - 予定コミット: `feat(posts): add creation timeline and detail routes`
3. [ ] **1-3** 本文・投稿者・公開状態・投稿IDを表示する一覧／詳細／作成フォームを追加する。成功後のリダイレクトと日本語エラーを共通レイアウトへ接続する。
   - 予定コミット: `feat(ui): add post creation and reading screens`
4. [ ] **1-4** 投稿テストと全テスト・lintを実行し、公開一覧に自己非公開投稿が混ざらないことをブラウザでも確認する。
   - 検証のみ。変更がなければコミット不要。

**受け入れ条件:**

- [ ] 未ログインでも公開投稿を閲覧できる。作成はログイン必須。
- [ ] 非公開本文を隠し要素や埋め込みデータにも含めない。

### Task 2: 自己投稿の本文編集を実装する

**目的:** 所有者が自分の投稿本文だけを更新できるようにする。

**変更ファイル（作成予定）:**

- `src/posts/repository.js`
- `src/routes/posts.js`
- `views/posts/edit.ejs`
- `views/posts/show.ejs`
- `tests/post-editing.test.js`

**サブタスク:**

1. [ ] **2-1** 正常編集、他人のID指定、user_id・is_publicの追加送信、CSRF欠落、SQL風本文、再読み込み後の保存結果を検証するテストを作る。
   - 予定コミット: `test(posts): cover ownership and edit boundaries`
2. [ ] **2-2** 編集フォームと更新処理を追加し、更新する列をbody・updated_atに固定する。SQLの更新条件に投稿IDとログイン利用者IDを含め、0件更新は404とする。
   - 予定コミット: `feat(posts): add owner-only body editing`
3. [ ] **2-3** 編集テストを実行し、他人の本文・投稿者・公開状態が変わらないことをDBでも確認する。
   - 検証のみ。変更がなければコミット不要。

**受け入れ条件:**

- [ ] 編集導線を隠すだけでなく、直接POSTでも他人の投稿を更新できない。
- [ ] 本文中の引用符が保存でき、所有者・公開状態は編集前後で変わらない。

### Task 3: 公開範囲を守る本文検索を実装する

**目的:** 後で所在を特定しやすい通常の検索処理と画面を作る。

**変更ファイル（作成予定）:**

- `src/posts/search.js`
- `src/routes/search.js`
- `views/search.ejs`
- `views/partials/header.ejs`
- `public/styles.css`
- `tests/search.test.js`

**サブタスク:**

1. [ ] **3-1** 未ログイン／ログイン時の公開範囲、空検索、日本語、引用符、%・_・エスケープ文字、SQL風文字列、件数上限、ダイジェスト非露出を検証する。
   - 予定コミット: `test(search): define safe search and visibility contracts`
2. [ ] **3-2** パラメーター化した本文の部分一致検索を独立したモジュールに実装する。公開範囲の条件を必須とし、必要な投稿列とusernameだけを取得する。
   - 予定コミット: `feat(search): add parameterized visible-post search`
3. [ ] **3-3** 共通検索欄、検索結果、0件表示、入力エラー、件数上限の案内を追加し、検索語と本文をエスケープして表示する。
   - 予定コミット: `feat(ui): add post search results`
4. [ ] **3-4** 全テスト・lintと検索のブラウザ確認を実行する。本人の非公開投稿が検索でき、他人のものはURLや検索語を変えても取得できないことを確認する。
   - 検証のみ。変更がなければコミット不要。

**受け入れ条件:**

- [ ] 検索には意図的な脆弱性や切替機構がない。
- [ ] SQL風文字列で権限のない投稿や別テーブル情報を取得できない。

## Plan内の依存関係

- Task 1 → Task 2 → Task 3の順に進める。後続Taskで変更した共通処理は、先行Taskのテストも実行する。

## 検証方法

- `npm test`：投稿、認可、公開範囲、検索、CSRF、HTMLエスケープを含む全テスト
- `npm run lint`
- 2アカウントで公開／非公開投稿を作り、一覧・詳細・編集・検索をブラウザ確認

- [ ] 引用符やSQL風文字列は入力値として扱われ、不正な更新や情報取得が起きない。
- [ ] 検索結果にもダイジェストは含まれず、HTMLとして入力が実行されない。
- [ ] 全Taskの受け入れ条件を満たし、必要なテスト・lint・表示確認が完了している。
- [ ] コードレビューの指摘を反映し、チェックリストに検証結果と実績コミットを記録した。
- [ ] head/baseを確認し、このPlanに対応するPRを1つ作成または更新した。

## 備考

- `/posts/new`は`/posts/:id`より先に解決し、idは正の整数として検証する。
- 本文1〜1,000文字、検索語最大100文字、一覧・検索最大50件は計画上の採用案。境界値と空白だけの本文をテストする。
- LIKE検索では入力の%・_・エスケープ文字をリテラルとして扱う。SQL構造と値の分離に加え、部分一致という検索仕様をテストする。
- 実績は[checklist-3.md](./checklist-3.md)へ記録する。
