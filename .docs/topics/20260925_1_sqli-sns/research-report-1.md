- Type: research-report
- Date: 2026-09-25
- Topic: sqli-sns
- Scope: 演習の土台となる通常の簡易SNSの機能、画面、データ、提供方法、受入条件と後続作業の区分
- Sources: 第5回 `connpass.md`、`proposal.md`、既存教材のREADME・一部実装（末尾のEvidence参照）
- 状態: 要件整理。アプリの実装・動作検証・デプロイは未実施。
- 要件の優先順位: 2026-09-25のユーザー指定を優先する。今回は意図的な脆弱性を入れず、通常の簡易SNSを作る。検索へのSQLインジェクション脆弱性の追加は後続作業とする。演習ガイド・SQL解説・初期化UI/API・別途の修正版は作らず、サーバー再起動で初期化する。`username`・`password`によるアカウント作成を必須とする。

## Summary

作るものは、**演習の土台となる、通常のテキスト投稿型SNS**。利用者はアカウントを作成し、自分の投稿を作成・編集して、閲覧可能な投稿を検索できる。

今回は検索を含む全機能に意図的な脆弱性を入れない。検索へのSQLインジェクション脆弱性の追加は、SNSの基本機能が完成した後の別作業とする。元企画にある4つの被害の再現は、今回の完成条件に含めない。

必須範囲は、アカウント作成、ログイン、投稿作成・編集、公開投稿の一覧・詳細、公開範囲を考慮した検索。初期状態への復帰はサーバー再起動で行い、アプリ内の演習ガイド・SQL解説・初期化機能・修正版は設けない。

構成案は、既存教材 `vulnerable-shop` のExpress・EJS・SQLite構成を参考に、第5回専用の小さなアプリを新設すること。既存アプリの全面流用や技術選定は確定事項ではない。

### 2. SNSとして必要な最小機能

以下の「必須」は元資料と今回の指定に対応する機能。「提案」は実装しやすくするための具体化であり、未確定。

| 機能 | 最小仕様 | 区分 |
| --- | --- | --- |
| アカウント作成 | `username`・`password`のみを入力して登録。同じ演習DB内でusernameは一意とし、空入力・重複を拒否。保存するのはパスワードダイジェスト | 必須／入力検証の詳細は提案 |
| ログイン | `username` と教材用パスワードで認証。画面にログイン中の利用者を表示 | 必須 |
| ログアウト | SNSのセッションを終了できる | 提案 |
| タイムライン | 公開投稿の本文・投稿者を表示。観察用に投稿IDと公開状態も表示する | 必須／表示項目の一部は提案 |
| 投稿詳細 | 再読み込みして本文・投稿者を確認できる。他人の非公開投稿は取得できない | 必須 |
| 投稿作成 | テキスト本文と公開／非公開を指定。投稿者はログイン情報から決める | 必須／公開範囲の入力UIは提案 |
| 投稿編集 | 自分の投稿本文だけを編集。サーバー側で所有者を確認し、投稿者IDは変更させない | 必須 |
| 投稿検索 | 本文で検索し、公開投稿と自分の非公開投稿を返す。他人の非公開投稿とダイジェストは返さない | 必須 |

検索を含むDB操作では、SQLと入力値を分離して扱うパラメーター化クエリなどを使用する。投稿編集の所有者確認、閲覧時の公開範囲の制限もサーバー側で行う。後で検索処理を変更する予定であっても、現段階で脆弱なクエリや脆弱性を有効化するスイッチは用意しない。

指定により対象外：意図的な脆弱性の実装、演習ガイド、SQL解説、初期化UI/API、別途の修正版と版の切替。

追加機能の対象外案：プロフィール編集、画像・動画、コメント、いいね、フォロー、DM、通知、外部SNS連携、メール、パスワード再設定、ランキング、採点・進捗管理。投稿削除と公開範囲の後編集も、最小のSNS機能に絞るため省く。

### 3. 今回と後続作業の区分

| 段階 | 作業範囲 | 完了の判断 |
| --- | --- | --- |
| 今回：SNSの土台 | アカウント作成、認証、投稿、閲覧、検索、再起動時の初期化 | 通常操作ができ、他人の投稿の不正編集や非公開情報の取得を防げる |
| 後続：検索の教材化 | 検索へのSQLインジェクション脆弱性の追加 | 別途決める演習シナリオと入力例で検証する。今回は実装・検証しない |

元企画には投稿改ざん・投稿者偽装・非公開投稿流出・ユーザー情報流出の4つの体験があるが、現在のSNS実装要件からは切り離す。後続作業の対象として指定されているのは検索であり、投稿編集への脆弱性追加は予定に含めない。検索を入口とする演習と元企画との整合は、後続作業で整理する。

検索処理は所在が分かる関数やモジュールにまとめる案とする。これは後から変更箇所を特定しやすくするためであり、脆弱版の実装や切替機構は作らない。

初期状態へ戻す必要があるときは運営者がサーバーを再起動する。再起動までは登録・投稿・編集の結果を保持する。

### 4. 画面構成案

ページ数を増やさず、通常のSNS操作に必要な画面に絞る。日本語UIとし、当日のノートPCで操作しやすいことを優先する。

| 画面 | 内容 |
| --- | --- |
| アカウント作成 | username・password入力、入力エラー・重複の表示。登録後はログイン画面へ移動する案 |
| ログイン | username・password入力、アカウント作成への導線 |
| タイムライン・検索 | 公開投稿一覧、検索欄、投稿作成への導線、検索結果。自分の非公開投稿は検索から到達可能 |
| 投稿作成 | 本文と公開範囲。保存後に投稿詳細へ移動 |
| 投稿詳細・編集 | 投稿ID・投稿者・本文・公開状態。所有者だけに編集導線を表示 |

共通部分にはログイン中のusernameを表示する。演習ナビゲーション、SQL表示、初期化ボタン、版の切替は配置しない。

### 5. データ設計案

教材DBの中心は2テーブルに限定する。

| テーブル | 列 | 用途 |
| --- | --- | --- |
| `users` | `id`, `username`, `password_digest` | アカウント登録、投稿者の識別、SNSログイン照合。ダイジェストは画面やAPIに返さない |
| `posts` | `id`, `user_id`, `body`, `is_public`, `created_at`, `updated_at` | 投稿・所有者・公開範囲・変更の保存。日時は表示用の追加案 |

初期データ案：AliceとBobの2アカウントに、それぞれ公開投稿と非公開投稿を用意する。短い架空の本文を使い、所有者と公開範囲による動作の違いを確認できるようにする。参加者が登録するアカウントとその投稿は、通常のアカウント作成・投稿作成で追加する。

初期アカウント・新規登録アカウントともに、入力したpasswordからダイジェストを生成し、ログイン時の照合に使う。DBの列は `password_digest` とし、平文passwordは保存しない。ハッシュ方式・パラメーターは実装着手時に選定する。メールアドレスは要求せず、教材用のusername・passwordを使う。

再起動時は教材DBを初期データに戻す。初期化対象には、新規登録アカウント、追加投稿、既存投稿の編集結果を含める。起動時に初期化を完了してからリクエストを受け付ける。セッションも無効化し、削除されたアカウントのIDを再利用した際に古いログイン状態が残らない設計とする。これらは「再起動で初期化」の具体化案。

Basic認証の秘密情報、SNSセッション、参加者と演習環境の対応情報は、後続の教材化も考慮して教材DBの外で管理する。参加者IDとSNSのユーザーIDは別の概念として実装する。

### 7. デプロイ・演習環境の要件

元企画の環境要件に、今回指定された再起動時の初期化を反映する。

- アカウント作成を含む教材ページ・APIをHTTPSとBasic認証で保護する。配信元への直接アクセスでも迂回できない構成にする。
- ブラウザの演習用セッションから、サーバー側で参加者のDBまたは実行環境を特定する。任意のDBパスや他参加者の環境IDを指定して切り替えられないようにする。
- 参加者別SQLiteファイル方式と、参加者別の実行環境方式を候補とする。現段階では通常のアクセスで環境を越えられないことを確認する。意図的なSQLインジェクションを追加した状態での分離検証は後続作業で行う。
- 初期化は運営者によるサーバー再起動で行う。同一サーバーが複数参加者のDBを管理する構成では、そのサーバー配下の全教材DBが初期化される想定とする。参加者別の実行環境を採用した場合は、再起動した環境が対象となる。
- username、投稿本文、検索語、取得した値はHTMLとして実行せず文字列として表示する。今回の演習にXSSやセッション窃取を混在させない。
- 開催後に環境を停止・削除する。保持期限と同時利用上限はデプロイ先と参加人数に合わせて決める。
- 公開教材には初期データ定義とサーバー起動・再起動手順を含める。ローカル実行時の待受はループバックを既定とする。

### 8. 完成と判断するための受入条件

| 分類 | 確認内容 |
| --- | --- |
| アカウント作成 | username・passwordだけで登録できる。同じ演習DB内のusername重複と空入力を拒否し、平文passwordをDBに保存しない |
| 通常操作 | 新規登録したアカウントでログイン、投稿作成、自己投稿編集、検索が成功する。誤ったパスワードではログインできない |
| 認可 | Bobの投稿を他の利用者が編集できない。投稿ID差し替えやフォームへの投稿者ID追加でも所有者を変更できない |
| 非公開情報 | Bob以外の利用者にはBobの非公開投稿をHTML・API・埋め込みデータに含めない。詳細URLの直接指定も確認する。ダイジェストは利用者を問わず応答に含めない |
| 入力とSQL | 検索・投稿編集などで引用符やSQL風の文字列がSQL命令として扱われない。通常の文字列として処理され、不正な更新や情報取得が起きない |
| 再起動時の初期化 | 新規登録・投稿追加・自己投稿の編集後にサーバーを再起動すると初期データへ戻る。追加アカウント・投稿は消え、古いセッションは使用できない |
| 参加者分離 | 独立した2つのブラウザ環境で、登録・投稿・編集が他参加者のDBに影響しない。他参加者の環境を参照できない。再起動による初期化範囲は採用構成と一致する |
| 配信 | Basic認証の保護範囲と配信元への直接アクセスを確認する |
| 表示 | username・投稿内容・検索結果が文字列として表示され、HTMLやスクリプトとして実行されない |
| 時間・負荷 | 想定参加人数で登録・投稿・検索が動作する。アカウント作成と必要な再起動時間を含めて進行を確認する |
| 復習 | 公開予定の手順だけでローカル起動と再起動による初期化ができ、同じ演習用SNSを利用できる |

アカウント作成と認証、認可と公開範囲、入力値とSQLの分離、再起動時の初期化、参加者分離を実装時の重点テストにする。脆弱性の再現は今回の受入条件に含めない。
