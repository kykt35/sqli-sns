# 起動とイベント運営

## 環境設定

`npm start` は `.env` を任意で読み込みます。Docker Composeは `.env` の値をコンテナへ渡します。実際の秘密値をGitへ登録しないでください。

| 変数 | 既定値 | 用途 |
| --- | --- | --- |
| APP_MODE | local | local / public |
| HOST | 127.0.0.1 | Nodeの待受。Compose内は0.0.0.0 |
| PORT | 3000 | Nodeの待受ポート |
| LOCAL_PORT | 3001 | Composeのホスト側ポート。127.0.0.1に限定 |
| MAX_POSTS | 1000 | SNS全体の投稿総数。初期4件を含む。4〜10,000 |
| MAX_USERS | 100 | SNS全体のアカウント総数。初期2件を含む。2〜1,000 |
| SESSION_TTL_MINUTES | 240 | 無操作時のセッション有効期限。1〜1,440分。DBの保持期限ではない |
| SESSION_SECRET | 起動ごとにランダム生成 | publicでは32文字以上の秘密値が必須 |
| BASIC_AUTH_USERNAME | 空 | 入口のBasic認証。passwordと対で設定 |
| BASIC_AUTH_PASSWORD | 空 | SNSアカウントとは別の共有認証情報 |
| TRUST_PROXY | 空 | publicで必須。HTTPSプロキシの実際のIP/CIDRをカンマ区切りで指定 |

シェルから継承した環境変数が `.env` より優先されます。設定不整合の場合は起動を中止します。ローカルでBasic認証を有効にする場合もusername / passwordの両方を設定してください。

## データと期限

SQLiteは起動時に1つだけ作成し、全利用者のアカウント・投稿を共有します。DBとサーバー側セッションは単一Node.jsプロセスのメモリ上にだけ存在します。同じブラウザのタブはセッションを共有し、別ブラウザは独立したログイン状態を持ちます。Cookieの削除や別ブラウザ利用でDBが増えることはありません。

セッションの期限切れではログイン状態だけを失い、共有DBのアカウントや投稿は保持されます。再ログインすると同じアカウントの投稿を利用できます。ログイン・ログアウト時にはセッションIDを変更します。DBの初期化はプロセスの再起動時だけです。

ブラウザごとのDB割り当てと50環境の枠は廃止しました。`MAX_ENVIRONMENTS` は使用しません。保存上限の設定名も `MAX_POSTS` / `MAX_USERS` に変更しています。アカウント処理は同時4件までで、超過時は503を返すため、時間を置いて再試行します。

投稿とアカウントの保存件数は、全利用者・公開／非公開を合算して制限します。SQLiteのトリガーで挿入時に判定するため、異なるブラウザからの同時登録でも件数上限を超えません。加えて共有DBは4KiB×2,048ページ（8MiB）までで、インデックスも容量に含みます。件数上限の設定が大きい場合は容量上限に先に達することがあります。

保存上限を超える投稿・登録・容量が不足する編集には507を返し、失敗した書き込みは保存しません。上限はSNS全体で共通なので、使い切ると他の利用者も新しい保存はできません。閲覧・検索・ログインは引き続き利用できます。件数上限では既存投稿の編集を許可します。ログアウト・Cookie削除・期限切れで上限はリセットされません。DB容量はプロセス全体のメモリ上限ではなく、セッション・処理中のメモリなどは別に必要です。

アカウントや公開投稿は参加者間で共有されます。非公開投稿は所有者としてログインしたセッションだけが閲覧でき、編集も所有者だけに許可します。Alice/Bobは共用の教材アカウントなので、参加者ごとの操作には新規アカウントを使用します。

## 限定公開

公開先にHTTPS終端プロキシを用意し、次を設定します。

- `APP_MODE=public`
- Basic認証のusername / password（SNS用の初期アカウントとは別に設定）
- 32文字以上のランダムな `SESSION_SECRET`
- プロキシの実際の送信元IPまたは必要最小限のCIDRを `TRUST_PROXY` に指定

秘密値の生成例は `node -e 'console.log(require("node:crypto").randomBytes(32).toString("hex"))'` です。生成値は運営者の設定先に保存します。

アプリはTLSを終端しません。プロキシ側でHTTPSを終端し、受信した `X-Forwarded-Proto` をプロキシ自身の正しい値で上書きしてください。アプリの待受に接続できる送信元も実プロキシに限定します。`TRUST_PROXY=true`、ワイルドカード、全IP範囲は使用できません。IPv4射影IPv6のCIDR表記も拒否するため、該当する範囲はIPv4 CIDRで指定してください。Dockerではアプリから見えるプロキシの送信元アドレスを確認して設定します。

publicでは、信頼したプロキシ経由のHTTPSと認識できないリクエストは426、Basic認証なし／不正は401になります。全ページ・静的ファイルを対象とし、セッション作成やルート処理の前に判定します。CookieにはHttpOnly・SameSite=Lax・Secureが付きます。実際の公開URLでログインとCookieが成立することを確認してください。

複数プロセス・複数レプリカや自動スケールには対応しません。運用は1プロセスに固定します。障害によるプロセス再起動でも全データが消えます。

## 再起動と終了

再起動は全参加者の操作・アカウント・投稿・ログインに影響します。運営側で実行タイミングを揃えてください。

- Node: `Ctrl+C` で停止し、`npm start` で起動。
- Compose: `docker compose restart` で初期化、`docker compose down` で終了。
- 公開環境: 採用したホスティングの停止・削除手順を開催前に確認。

公開前には、担当運営者が公開URL、HTTPS、実プロキシ設定、直接アクセス制限、想定人数での性能、終了時の停止・削除を確認します。詳細な未検証項目は[検証記録](verification.md)に記載します。
